# A59 — `fixtures/baked/` has no regeneration path, and the README implies it does

**Lane:** mobile (the fixture is consumed by `FixtureBundleTest`), with a `core/` + `Makefile` edge.
**Size:** S. **Status:** spec, not started.
**Raised by:** Fable during the A58 review; filed at VLL's instruction, 2026-09-02.

## The finding

`app/shared/src/commonTest/resources/fixtures/README.md` says, of the fixtures as a whole:

> **Do not hand-edit.** They are generated by the dev tool `core/cmd/mkbundle` and are deterministic
> (same flags ⇒ byte-identical output), so regenerating should produce an empty diff. Regenerate
> with: `make fixtures`

That is true of `demo/` and `torture/` — and **not** of `baked/`. `make fixtures` runs `mkbundle`
with `-out …/demo` and `-torture …/torture`; **`baked/` is not an output of that command at all.**
It is a genuine `web/bake`-produced bundle, committed as a frozen snapshot, and consumed by
`FixtureBundleTest.realBakerBundle_loadsPerformable`.

So the README's blanket claim is wrong for one of its three fixtures, and the one it is wrong about
is the only one that guards the **real** baker's output shape. If the bundle format changes,
`demo/` and `torture/` are regenerated and keep passing while `baked/` silently keeps asserting the
old shape — the guard quietly stops guarding, which is worse than not having it.

## What this is deliberately *not*

`baked/` being frozen is not itself the bug — a snapshot of a real producer is exactly what makes
that test worth having. **The bug is that nothing says so, and the README says the opposite.** Do
not "fix" this by regenerating `baked/` with `mkbundle`: that would replace a real-baker artefact
with a synthetic one and delete the only thing the test is for.

## Work — pick one, and say which

1. **Wire a real regeneration target.** `make fixtures-baked` runs the actual bake pipeline
   (poppler + the Node `web/bake` worker) into `fixtures/baked/`. Honest, but it needs the full
   toolchain, so it **cannot** be part of plain `make fixtures` and must **skip with a clear message**
   when node/pdftoppm/the built CLI are missing — see [T128](T128-the-bake-toolchain-fails-at-the-gig-not-at-boot.md),
   which is about that exact toolchain being resolvable in the first place. Land T128 first if both
   are queued; this task inherits its resolution.
2. **Or document it as frozen, properly.** Correct the README so the "regenerate with `make
   fixtures`" claim is scoped to `demo/` and `torture/`, and give `baked/` a recorded recipe: which
   commit, which setlist, which flags, and the command a human would run to remake it by hand.

**Recommendation: (2) now, (1) later.** Option 2 removes the false claim today for the cost of a
paragraph, and a false claim in a README is the active harm. Option 1 is the better end state but
drags in the whole bake toolchain, and is not worth blocking the correction on.

## Done when

- No document claims `make fixtures` regenerates `baked/` unless it actually does.
- `fixtures/README.md` states, per fixture, what produces it and how to remake it.
- If (1) is taken: running the target on a machine **without** node or pdftoppm **skips with a
  readable message** rather than failing or, worse, writing a half-made fixture. Test that path
  deliberately — it is the one contributors will hit.
- If (1) is taken: regenerating on a clean checkout produces an **empty diff**, or the README says
  plainly that it does not and why.
- `:shared:testDebugUnitTest` still reports **303**. Match the count.
